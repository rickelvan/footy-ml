## 1) What the dashboard is

`ml_dashboard.html` is a self-contained, presentation-style dashboard that combines:

- **Season analytics visuals** (team projections, discipline watchlist, breakout candidates).
- **xG (expected goals) model training + evaluation visuals** (metrics, learning curve, comparisons, confusion matrix, feature importance, model comparison).
- **Game outcome predictions (1X2)** trained from completed match results (Home/Draw/Away probabilities in a table).

The dashboard is generated by the pipeline entrypoint:

- `python -m footy_xg_model.main`

## 3) How datasets are processed, managed, and integrated

### 3.1 Configuration and “single source of truth”

All core configuration (paths, random seed, feature lists, tuning parameters, projection thresholds) is centralized in:

- `footy_xg_model/config.py`

Important examples:

- `PROJECT_ROOT` resolves the project root directory.
- `RAW_PLAYER_SEASON_PATH` is the default player-season CSV.
- `DATA_OUT_DIR` is the dashboard artifacts directory (`footy_xg_model/artifacts/`).
- `RANDOM_SEED` ensures deterministic shot-level example construction and reproducible splits.

### 3.2 Data loading and basic validation

#### Player-season loading

`footy_xg_model/data_loader.py`:

- Reads the CSV.
- Performs basic checks (required columns exist).
- Coerces numeric columns to numeric.
- Fills obvious missing values (e.g., `appearances`, `goals`).
- Normalizes position labels for downstream grouping.

This keeps ingestion deliberately lightweight: the system prioritizes **getting a clean DataFrame into the pipeline** with minimal assumptions.

#### Completed matches loading

`footy_xg_model/match_predictor.py`:

- Reads the CSV.
- Filters to `status == "completed"`.
- Parses `match_date` into datetime (when present).

### 3.3 Integration in the final dashboard

The dashboard is built from two parallel data streams:

1. **Player-season stream** → season analytics visuals + shot-level examples → xG visuals
2. **Completed matches stream** → match outcome model → 1X2 probability table

The dashboard merges these streams into one page so the user can view season insights, xG model diagnostics, and game predictions together.

## 4) Full workflow (“A to Z”) from input to the final dashboard

The pipeline runs in `footy_xg_model/main.py` and can be summarized as:

### Step A — Load player-season data

Input:

- Player-season CSV (default from `config.RAW_PLAYER_SEASON_PATH`).

Output:

- `player_season_df` (cleaned DataFrame).

### Step B — Season analytics (player → team → projections)

Module:

- `footy_xg_model/season_analytics.py`

Key actions:

1. **Player feature engineering**:
   - per-game rates: goals/game, assists/game
   - discipline scoring
   - a composite **performance_score**
2. **Team aggregation**:
   - totals and derived rates (e.g., goals per appearance)
3. **Goal prediction regression model (player-season level)**:
   - candidates: Ridge, Random Forest Regressor, Gradient Boosting Regressor
   - selection method: Leave-One-Out cross-validation (good for small datasets)
4. **Next-season projections**:
   - projects appearances/goals/assists/cards for the next season
   - aggregates projected player values to the team level
5. **Derived insights**:
   - discipline risk list
   - breakout candidate list

Outputs:

- season analytics tables and projections that drive the dashboard’s “Season analytics” visuals:
  - team projection cards
  - discipline watchlist cards
  - breakout candidate cards

### Step C — Prepare shot-level dataset for xG

Module:

- `footy_xg_model/preprocessing.py`

Problem:

- xG requires shot-level examples, but the available dataset is player-season aggregates.

Output:

- `shots_df`: one row per shot example with target label `is_goal`

### Step D — Engineer football-aware shot features

Module:

- `footy_xg_model/feature_engineering.py`

Adds:

- `shot_distance`: Euclidean distance to goal centre
- `shot_angle`: a bearing-style approximation of shooting angle

Defines model feature set in `build_feature_target_matrices`:

- Numeric features from `config.NUMERIC_FEATURES` + `under_pressure`
- Categorical features from `config.CATEGORICAL_FEATURES`

Outputs:

- `X` feature matrix and `y` label vector (goal vs no-goal)

### Step E — Split into train / validation / test

Module:

- `preprocessing.train_test_split_shots`

Approach:

- stratified split on `is_goal` to preserve class balance in both sets

Outputs:

- train set, validation set (derived from train), test set

### Step F — Train multiple xG models and tune hyperparameters

Module:

- `footy_xg_model/train_model.py`

What happens:

1. Build preprocessing pipeline:
   - `StandardScaler` for numeric features
   - `OneHotEncoder` for categorical features
2. Train/tune candidate algorithms via `GridSearchCV` with k-fold CV:
   - logistic regression
   - random forest classifier
   - gradient boosting classifier
3. Objective:
   - optimize for **log loss** (probabilistic quality)

Outputs:

- tuned pipelines for each candidate model
- CV results for transparency

### Step G — Select the best xG model and calibrate probabilities

Selection:

- uses held-out validation log loss

Calibration:

- wraps the classifier in `CalibratedClassifierCV` using **isotonic regression**
- calibration is crucial because xG is fundamentally a probability (not just a yes/no label)

Output:

- calibrated xG pipeline saved to:
  - `footy_xg_model/models/best_calibrated_xg_pipeline.joblib`

### Step H — Evaluate the xG model

Module:

- `footy_xg_model/evaluate_model.py`

Scalar metrics computed:

- log loss
- ROC AUC
- Brier score
- precision@0.5 and recall@0.5 (threshold-based)

Dashboard-facing evaluation artifacts:

- the dashboard’s **metrics cards** use computed scalar metrics (accuracy, precision, recall, ROC AUC, log loss, Brier score)
- the dashboard’s **confusion matrix** panel visualizes confusion counts as a heatmap (random baseline vs trained)
- the dashboard’s **feature importance** chart uses extracted/constructed feature weights

### Step I — Train the match outcome model (1X2)

Module:

- `footy_xg_model/match_predictor.py`

Target label:

- `H` if `home_score > away_score`
- `D` if draw
- `A` if away wins

Features:

- categorical: `home_team_name`, `away_team_name`, `season_code`
- numeric: `match_month`, `match_dow` derived from `match_date`

Model:

- multinomial logistic regression

Evaluation:

- a simple **time-based split**: older matches for training, newer matches for testing
- report test accuracy in dashboard metadata

### Step J — Generate end-user outputs (report + dashboard)

#### Interactive dashboard (the only deliverable covered by this report)

Module:

- `footy_xg_model/visualization_dashboard.py`

Output file:

- `footy_xg_model/artifacts/ml_dashboard.html`

What the dashboard contains:

- season visuals (team projections, discipline watchlist, breakout cards)
- xG metrics cards
- learning curves (simulated “epoch-like” history for storytelling)
- before/after comparison (random baseline vs trained model)
- confusion matrix heatmaps
- game outcome prediction table (1X2 probabilities from completed matches)
- feature importance chart
- model comparison chart

Operational modes:

- offline: the HTML is self-contained
- online retrain: when served via Flask (`footy_xg_model/dashboard_server.py`), users can upload a CSV and trigger a rebuild

## 5) How predictions are generated (The Python/Technical Bit)

The system relies heavily on `scikit-learn` to build, train, and calibrate its models. The pipeline approach (`sklearn.pipeline.Pipeline`) ensures that data transformations and model training are bundled together cleanly.

### 5.1 Season-level predictions

The season analytics pipeline generates **player projections** (goals, assists, appearances, discipline) for the next season, which are aggregated into **team projections**.

These are driven by:

- interpretable per-game rates and explicit projection heuristics.
- a regression model predicting goals. 

**Under the hood:**
The system evaluates multiple regressors using `sklearn` cross-validation:
- `sklearn.linear_model.Ridge`
- `sklearn.ensemble.RandomForestRegressor`
- `sklearn.ensemble.GradientBoostingRegressor`

Because the player-season dataset is typically small, the pipeline determines the best model via Leave-One-Out Cross-Validation (`sklearn.model_selection.LeaveOneOut` combined with `cross_val_score`). Categorical player features are encoded safely via `LabelEncoder`.

### 5.2 xG (shot probability) predictions

The xG model predicts the probability of a goal: \\(P(\\text{goal} \\mid \\text{shot features})\\).

**Under the hood:**
The feature processing relies on `sklearn.compose.ColumnTransformer`:
- Numeric features are scaled using `StandardScaler`.
- Categorical features (like `shot_type` or `play_pattern`) are encoded using `OneHotEncoder`.

Model selection uses grid search (`sklearn.model_selection.GridSearchCV`) optimizing for `log_loss` across several classifier architectures:
- `LogisticRegression`
- `RandomForestClassifier`
- `GradientBoostingClassifier`

Because xG is fundamentally a probability assessment and some tree-based models can be poorly calibrated out of the box, the pipeline wraps the chosen optimal classifier in `sklearn.calibration.CalibratedClassifierCV` using an isotonic regression wrapper. This guarantees that if the model predicts a 0.2 xG, roughly 20% of such shots result in goals.

### 5.3 Match outcome (1X2) predictions

The match model predicts the probabilities of Home Win, Draw, or Away Win: \\(P(H)\\), \\(P(D)\\), \\(P(A)\\).

**Under the hood:**
This classifier addresses a multi-class problem (Home, Draw, Away). Data preparation similarly uses a `ColumnTransformer` to apply `OneHotEncoder` onto categorical features like `home_team_name` and `away_team_name`.

The outcome model leverages `sklearn.linear_model.LogisticRegression` configured as a multinomial classifier. Instead of a random split (which would leak future team performance into past match predictions), the evaluation relies on a chronological slice: using older matches for training and testing against recent matches, predicting realistic game outcomes in a rigorous, time-aware manner.

## 6) Evaluation: usefulness and effectiveness of the predictions

This system produces multiple kinds of predictions; their usefulness depends on data realism and decision context.

### 6.1 Season analytics usefulness

Strengths:

- Very useful for **ranking**, **summarization**, and **planning** in low-data environments.
- Projections and flags are interpretable and configurable.
- Team aggregation is actionable for coaches/managers (“who contributes?”, “who is at risk?”).

### 6.2 xG model usefulness

Strengths:

- Treats xG as a proper probability problem (log loss + calibration).
- The dashboard/report explain probabilistic interpretation clearly.
- Geometry features are football-consistent and interpretable.

### 6.3 Match outcome model usefulness

Strengths:

- Directly models game outcomes from real match results.
- Produces interpretable probabilities.
- Time split reduces look-ahead bias compared to random splits.

## 8) How to run the system (end-to-end)

From the project root:

1. Run the full pipeline:
   - `python -m footy_xg_model.main`
2. Open outputs:
   - `footy_xg_model/artifacts/ml_dashboard.html`

### Serve the Flask app (online CSV retrain)

The Flask server enables the dashboard’s CSV upload + retrain flow.

1. Install Flask (once):
   ```bash
   pip install flask
   ```
2. Start the server (from the project root):
   ```bash
   python -m footy_xg_model.dashboard_server
   ```
3. Open:
   - `http://127.0.0.1:8765/`
4. Upload a new player-season CSV using the dashboard’s CSV drop zone:
   - the server saves the CSV to `config.RAW_PLAYER_SEASON_PATH`
   - the server runs the full pipeline in a background thread
   - progress can be checked at `GET /api/status`
